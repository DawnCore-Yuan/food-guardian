# 排行榜｜規則、計分依據與伺服器檢查

> 本檔說明「哪些成績可以上榜、為什麼」，以及這些檢查的界線。
> 所有內容皆為合理性檢查，**不是**完整防作弊。

## 1. 計分依據（上限從規則算出來，不是猜的）

| 項目 | 數值 | 來源 |
|---|---|---|
| 沙門氏菌 26 隻 × 200 | 5,200 | `src/data/enemies.ts`、`src/systems/waves.ts`（v2 七段波次） |
| 黃麴毒素 14 隻 × 150 | 2,100 | 同上 |
| 二氧化硫超標 12 隻 × 180 | 2,160 | 同上 |
| 金黃色葡萄球菌 11 隻 × 150 | 1,650 | 同上 |
| 擊破總分 | **11,110** | `waveStats()` 展開波次逐群加總，共 **63** 隻 |
| 通關生命獎勵 5 × 200 | 1,000 | `BALANCE.player.hp`、`BALANCE.score.hpBonusPerLife` |
| 設定理論上限 | **12,110** | 擊破全滿＋滿血通關 |
| 伺服器硬上限 | **12,500** | 12,110 向上取整至 500 |

擊破數上限 63 = 波次設定總生成數。**這是設定值，不是保證值**：實際生成受敵人容量（16）限制，
若某一刻在場已滿，該隻會被跳過（`spawnSkippedCap`），因此「實際可擊破數 ≤ 63」。
設定上的理論上限與受容量限制的實際值分開記錄；實際峰值與跳過次數以瀏覽器實測填寫（見第 6 節）。

## 2. 時間規則（以伺服器為準）

- 單局憑證由 `leaderboard-start` 核發，`issued_at` 是**伺服器時間**，有效期 20 分鐘。
- 提交時伺服器計算 `serverElapsed = now() − issued_at`：

| 情境 | 判定 | 結果 |
|---|---|---|
| won，serverElapsed ≥ 180 秒 | 通過 | 可登錄 |
| won，serverElapsed < 180 秒 | 客戶端宣稱通關但伺服器沒過 180 秒 | 拒絕（`bad_time`） |
| lost，elapsed 在伺服器經過時間內（無任意下限） | 通過 | **允許 180 秒前正常陣亡登錄** |
| 遊戲時間 > 伺服器經過時間 + 3 秒 | 回報時間比現實還長 | 拒絕（`bad_time`） |
| 遊戲時間 > 伺服器經過時間 + 3 秒 | 回報時間比現實還長 | 拒絕（`bad_time`） |
| 超過憑證有效期才提交 | 已過期 | 拒絕（`ticket_expired`） |

**暫停與輸入暱稱不會誤殺**：遊戲在暫停時 `RunState` 不累加，但伺服器時鐘照走；因此
`serverElapsed ≥ 遊戲時間` 恆成立，只用「上限」方向檢查。通關後停 10 分鐘輸入暱稱仍可登錄。

## 2.1 分數與擊破數的相符規則（逐擊破數上限）

只檢查「分數 ≤ 擊破 k 隻理論最高分 ＋ 通關生命獎勵」，不假設時間到時所有敵人已擊破或逃脫，
因此**不要求 `kills + escapes = 63`**。

- 擊破 k 隻最高擊破分＝官方敵人分值由高到低（200 / 180 / 150 / 150）取前 k 隻總和。
- 通關加生命獎勵上限 5 × 200 ＝ 1,000；未通關不得含獎勵。

| kills | 擊破分上限 | 通關上限 | 未通關上限 |
|---|---|---|---|
| 0 | 0 | 1,000 | 0 |
| 10 | 2,000 | 3,000 | 2,000 |
| 61 | 10,810 | 11,810 | 10,810 |
| 62 | 10,960 | 11,960 | 10,960 |
| 63 | 11,110 | 12,110 | 11,110 |

例：通關 62 隻、擊破 10,960 ＋ 少一隻二氧化硫？→ 實際合法例為 11,110 − 180 ＋ 1,000 ＝ **11,930**，上限 11,960，可登錄。
舊版固定門檻（`score > 11,110 + 200 且 kills < 63`）會誤擋此案例，已移除。

## 3. 「不是完整防作弊」的說明

伺服器能做的：拒絕不合理欄位、拒絕憑證不符、拒絕重複局、拒絕時間不成立的分數、限制頻率。
伺服器**做不到**的：分辨「真的打到 12,110 分」與「改瀏覽器把分數填成 12,110、時間填成 181 秒」。
玩家改前端後仍可送出「落在合理範圍內」的假分數；本設計只把門檻從「任意輸入」提高到「必須符合計分與時間模型」。

## 4. 後端實作核對表

| 問題 | 實作 | 證據等級 |
|---|---|---|
| 同時送出的重複請求 | `scores.ticket_id UNIQUE`；插入為單筆 INSERT，第二筆由資料庫回 409，函式改查既有紀錄回同名次 | SCHEMA（未在雲端同時打過） |
| 重送時驗證 ticket/token | 每次呼叫先 `leaderboard_ticket(id, token_hash)`，不符即 403；**不存在**只憑 ticket_id 取資料的路徑 | 程式碼 |
| 相同分數／相同時間戳的排序 | `order by score desc, created_at asc, id asc`；列表與名次都取 `v_scores_public.rank` | SCHEMA |
| 限流跨實例 | `leaderboard_rate_limited` 在資料庫內以 `now()` 計數（tickets 12/10 分、scores 20/10 分）；**不具並行原子性**（兩請求可同時讀到同一計數而一起通過），真正硬約束是 `scores.ticket_id` 唯一 | 程式碼＋文件說明 |
| 關閉 Verify JWT 後靠什麼 | 版本白名單、單局 ticket＋token、資料庫 CHECK 與唯一約束、資料庫端限流；anon key 與 CORS 只決定「誰能呼叫」，不是身分驗證 | 程式碼 |
| 公開端能讀什麼 | 只有 `leaderboard-list` 回傳的 rank/nickname/score/outcome；資料表 REVOKE ALL、RLS 無政策 | SCHEMA |

## 6. v2 七段波次（難度曲線）

| 段 | 時間 | 計畫生成 | 段內最短間隔 | 敵人組合 | 行為壓力 |
|---|---|---|---|---|---|
| P1 | 0–30 秒 | 7 | 4,000 ms | 沙 5、黃 2 | 直線坦克＋波浪；無敵彈 |
| P2 | 30–60 秒 | 8 | 2,800 ms | 沙 4、黃 2、二 2 | 首次出現射手（敵彈） |
| P3 | 60–90 秒 | 9 | 2,400 ms | 沙 3、黃 2、二 2、葡 2 | 四敵混合；換線行為登場 |
| P4 | 90–120 秒 | 11 | 2,000 ms | 沙 4、黃 2、二 2、葡 3 | 間隔縮短，組合壓力上升 |
| P5 | 120–150 秒 | 12 | 1,800 ms | 沙 4、黃 3、二 3、葡 2 | 生成數最高 |
| P6 | 150–170 秒 | 11 | 1,500 ms | 沙 4、黃 2、二 2、葡 3 | 最後衝刺；含 165,000 ms 起同群 200 ms 併發 |
| P7 | 170–180 秒 | 5 | 1,400 ms | 沙 2、黃 1、二 1、葡 1 | 維持高潮、不新增機制 |

- 178–180 秒不再生成；最後一隻於 176,000 ms（176 秒）出場，仍有約 4 秒可交戰。
- 全表最短生成間隔為 **200 ms**（P6 內 165 秒起同群兩隻）；其餘群組間隔 900–4,000 ms。
- 段與段之間保留 1–2 秒喘息。
- 未改：敵人血量／傷害／速度、玩家射速、碰撞體、預警 600 ms、容量（敵人 16／敵彈 12／預警 3）。
