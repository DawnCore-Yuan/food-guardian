# 音效事故回顧（AUDIO-INCIDENT-REVIEW）

記錄區間：2026-10-21，專案 food-guardian 加入 Web Audio 音效至恢復有聲的過程。
本文件只記錄「有證據的結論」與「仍未確認的疑點」，兩者分開寫。

---

## 一、已確認

### 1. 最初無聲：voice Gain 初值為 0

- 實際播放路徑 `src/systems/audio.ts` 的 `spawn()` 內，voice 增益層建立時 `gain.gain.value = 0`，且該層**從未被任何包絡排程**。
- 所有聲源都接到這一層，因此輸出被乘成零。
- 逐步排除的離線量測（同一 OfflineAudioContext）：
  | 結構 | peak |
  |---|---|
  | 固定 gain 0.5 對照音（無包絡） | 0.5 |
  | 加上包絡、voice 直接接 destination | 0.0995 |
  | 完整 spawn 結構（voice gain = 0 + master 0.9） | **0** |
- 修正：voice gain 初值改為 `1`（提交 `82a3199`）。該層仍保留給 `stopAll` 歸零與 `kill()` 停止用。
- **使用者實測確認有聲。**

### 2. 後續回歸：83f9239 之後再次無聲

- `83f9239` 同時做了兩類修改：音色重寫（波形／頻率／層數）與聲源容量管理（`MAX_SOURCES`、`trackSource()`、`hasSourceRoom()`、`SOURCE_NEED`，`spawn()` 開頭容量不足即 return null）。
- **使用者實測回報再次無聲。**

### 3. 恢復：da202e2

- 以 `git checkout 82a3199 -- src/systems/audio.ts` 只還原該檔，未 reset、未整專案退版。
- HUD、首頁音效文字、時間列等修改全數保留。
- **使用者實測確認聲音恢復。** 此版本為目前唯一人工確認有聲的音效基準。

---

## 二、尚未確認

- **第二次回歸的具體程式原因未確認。**
- 音色重寫與聲源容量管理是**同時**進入的，現有證據無法區分是哪一項（或兩者組合）造成無聲。
- 不可把「泛音」或「容量管理」任何一項寫成已確定根因。
- 後續若要恢復音色層次，必須**一次只套一類**，各自驗證、各自提交。

---

## 三、曾經無效或誤導的驗證方式

以下做法在本次事故中出現過，且沒有提供有效證據：

| 做法 | 為什麼不算證據 |
|---|---|
| `scheduled`／`state=running` 當作「有聲音」 | 只代表 API 排程成功或 context 在跑，不代表裝置有輸出 |
| 診斷頁在正式版 import `/src/*.ts` | 靜態 build 不含 `src/`，模組載入失敗 |
| 離線測試另寫一份合成常數表 | 沒有經過實際 `spawn()`，結果不代表正式播放路徑 |
| 用總發聲數推論單一音效 | 不同音效混在一起計數 |
| 用頻率反推音效種類 | 波形重疊時無法區分 |
| 並行跑多個案例後判讀 | 前一個案例的殘留聲音污染後一個 |
| 未核實就歸因於低幀率 | 沒有量測幀間隔與 tick 次數 |
| 未核實就歸因於 async／await | 建立與 resume 都在第一個 await 之前 |
| 未核實就歸因於 iPhone／系統設定 | 桌面同樣無聲，未排除即結論 |
| 只用點座標比較是否重疊 | 必須用完整矩形（left/top/right/bottom） |

## 五、下次要改音效時的前置條件

1. 先確認目前版本有聲（使用者實聽）。
2. 一次只改一類：先音色，或先容量管理，不要同時。
3. 每類改完立刻 commit、build、交付實聽，通過後才動下一類。
4. 若再次無聲，立刻用 `git checkout <已知有聲 commit> -- src/systems/audio.ts` 單檔回復。
5. 任何「排程成功」的紀錄，都只能寫成「已排程」，不能寫成「有聲音」。
